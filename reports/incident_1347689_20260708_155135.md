# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
The teacher is reporting that the lock rules feature is not functioning as expected for the "Ready, Set, Grow! (American English) Level 1" course in the Home Practice section. Although the teacher successfully creates and saves a lock rule through the "Manage student's access" interface and receives a confirmation message, the selected exercises remain completely unlocked and accessible to students.

## Initial Assessment
*   **Platform:** Cambridge One (C1)
*   **Product:** Ready Set Grow! (American English) Level 1
*   **Affected Class Code:** 92h2-mQi7
*   **Affected Component/Path:** Manage Student Access > Home Practice
*   **System Area:** Lock Rules Engine / Entitlement Validation

## Common Patterns Identified
*   **Platform-Wide Symptom:** Across multiple Cambridge One incidents (Ticket 1299299, Ticket 1312794, Ticket 1038544), teachers attempt to configure lock rules, but the platform fails to enforce the restriction properly.
*   **Rule Corruption State:** In previous cases where a rule was successfully created in the UI but did not execute correctly on the student side, the root cause was identified as a corrupted Lock Rule entity in the database.
*   **The "Save/Re-save" Interaction:** Opening the existing rule and saving it again without modifications has historically cleared the corrupted state and forced the database/access engine to sync correctly.

## Root Cause Analysis

### Confirmed causes
*   **None at this stage:** The automation script failed to bypass the initial login phase due to a timeout on the post-login "Hi Litmus!" verification element, preventing direct automated validation of the rule state.

### Suspected causes
*   **Lock Rule Entity Corruption:** Similar to Ticket 1299299 and Ticket 1312794, the lock rule for the Home Practice section may have saved in a corrupted state, meaning the UI displays the rule as active, but the backend entitlement validation engine is not evaluating or enforcing it.
*   **Delayed Item Association (As Per Design):** Similar to Ticket 1038544, there may be a discrepancy between the exact items selected during rule creation and the items the students are accessing, or a synchronization delay between the database and the client-side UI.
*   **Unresolved Non-Lockable Components:** Based on Jira ticket **NEMO-21735**, the Home Practice section of this specific product might contain non-lockable components that are bypassable.

### Missing evidence
*   API/Application logs matching class `e714cef1-e9f4-41f2-903c-052710c9e430` to verify if the rule payload is accurately registered.
*   The exact Rule ID associated with this "Home Practice" lock configuration.
*   Student submission and access timestamp logs to cross-reference against the lock rule creation timestamp.

## Actions Performed in Similar Incidents
*   **Ticket 1099646:** Replicated rule-saving issues, verified user scopes, and tracked resolution under **COS-1424** (deployed to THOR).
*   **Ticket 1299299:** Replicated the access issue using the affected user's account, identified the specific corrupted Lock Rule, and performed an "open and re-save" action to clear the backend corruption.
*   **Ticket 1312794:** Analyzed application logs, verified Gigya tokens, located the specific corrupted Rule ID, and re-saved the rule to restore proper validation. Linked to **COS-2229** for **RED team** investigation.
*   **Ticket 1038544:** Verified rule creation timestamps and modification logs via API logs, cross-referencing them against student submission timestamps to confirm design-compliant behavior.

## Recommended Investigation Steps
1.  **Retrieve Rule ID and Logs:** Search the application logs for class `e714cef1-e9f4-41f2-903c-052710c9e430` and class code `92h2-mQi7` to identify the specific Lock Rule ID generated when the teacher clicked "Save" (Reference: Ticket 1312794).
2.  **Verify Item Configuration:** Cross-reference the specific Home Practice activity codes with the items registered in the lock rule payload to ensure they are explicitly included (Reference: Ticket 1038544).
3.  **Perform Rule Re-Save:** Have a support engineer or the teacher open the active lock rule for "Home Practice", make no changes, and click "Save" again to attempt to clear any database serialization/corruption issues (Reference: Ticket 1299299, Ticket 1312794).
4.  **Analyze Component Compatibility:** Check if the affected "Home Practice" material contains non-lockable components under the scope of **NEMO-21735**.

## Recommended Resolution Path
If the investigation confirms the rule exists but is ignored by the system:
1.  **Workaround:** Direct the teacher to delete the current rule, clear browser cache, and recreate/re-save the "Home Practice" lock rule.
2.  **Escalation:** If re-saving does not apply the lock, escalate the Rule ID and Class ID to the **RED team** referencing **COS-2229** and **COS-1424** for backend database alignment.

### Explanation
While the platform (Cambridge One) and the core functional symptom match historical lock rule failures perfectly, the replication script failed at the login step. We cannot confirm with 100% certainty whether this is a corrupted rule entity (Ticket 1299299) or an item-association delay (Ticket 1038544) without backend log access to the class.
