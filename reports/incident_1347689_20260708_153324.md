## Common Patterns Identified
Across the historical incidents on the **Cambridge One** platform, the following recurring technical patterns associated with the Lock/Unlock functionality were identified:
- **Lock Rule Corruption:** Existing rules can become corrupted in the system. While the front-end UI may show that a rule is saved, the underlying validation fails to enforce the restriction or misinterprets the rule's active state (as seen in Ticket 1299299 and Ticket 1312794).
- **Out-of-Sync Rule Scope / Removed Users:** Removing a student who is tied to a specific user-scope lock rule corrupts subsequent rule evaluations or updates, causing save errors or processing failures (as seen in Ticket 1099646 under COS-1424).
- **Configuration Delay or Item Code Mismatch:** Lock configurations may successfully save for a unit but fail to immediately map to specific underlying exercise ItemCodes, leaving items unlocked if students access them before the mapping is finalized (as seen in Ticket 1038544).

### Suspected Causes
- **Corrupted Lock Rule Configuration:** Similar to Ticket 1299299 and Ticket 1312794, the system may have written a corrupted lock rule state for the "Home Practice" section of this class. The UI shows the rule is created, but the backend is not actively enforcing the lock state.
- **Removed Student Scope (Orphaned Rules):** Similar to Ticket 1099646 (COS-1424), if a student was previously removed from the class `92h2-mQi7` while having an active access rule, it may prevent new class-level lock rules from being fully processed or applied.
- **Unmapped Content / Item Codes:** Similar to Ticket 1038544, the specific digital assets or activities in "Home Practice" might not be correctly mapped to the Lock rule schema, allowing students to bypass the restriction.
