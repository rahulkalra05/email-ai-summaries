# Operational Incident Investigation Report

## Incident Number
1363886

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
The English Technology Platform Support Team reported that users are experiencing download issues within the Cambridge One (C1) desktop application, where downloading eBooks consistently gets stuck or suffers from extreme slowness. While support agents were able to bypass the stall by pausing and resuming the download, the reporting user notes that pausing and restarting does not resolve the slowness, even when operating on a high-speed 300 Mbps internet connection. 

## Initial Assessment
*   **Likely Affected System:** Cambridge One (C1) Desktop Application
*   **Affected Products:** eBooks / Presentation Plus components
*   **Affected Components:** Download Manager / Unzip Module (Desktop Client UI progress handling, background downloader, and local extraction process)

## Common Patterns Identified
*   **UI/UX Disconnect (Progress Bar Stalls):** A primary pattern is that the visual progress bar in the Cambridge One Desktop App often freezes (typically at 0%, 2-3%, or 98%) while background activities are actually succeeding. This is frequently triggered by products containing a high number of units (100+ units or ~150 linked PE units).
*   **Background Extraction Overhead:** The desktop application downloads multiple small zip files (meta.zip/PE units) and unzips them sequentially. During this intensive I/O process, the UI progress bar fails to update dynamically, leading users to believe the download has failed or timed out.
*   **Pause/Resume Workarounds:** In multiple historical cases, clicking "play" (resume) or restarting the application acts as a manual trigger to force the UI/background sync to catch up or retry a interrupted/corrupted zip sequence.

## Root Cause Analysis

### Confirmed Causes
*   No confirmed root cause can be definitively selected for the current ticket without deeper technical logging, but historical data confirms that the desktop app's UI progress calculation frequently fails or lags when handling eBooks with a high volume of units (PEs).

### Suspected Causes
*   **UI Feedback/Timer Reset:** The application may be suffering from a visual feedback loop where the download timer continuously resets due to minor network fluctuations or sequential processing of small zip files (similar to Ticket 1077440).
*   **Unzipping Block / Corrupted Files:** The download process might be halting on a specific corrupted or incomplete segment, preventing the unzip module from initiating (similar to Ticket 1043393).
*   **Progress Calculation Bug:** If the eBook contains a large number of units, the application's percentage calculator may be failing to update, making a functional background download look entirely stalled (similar to Ticket 938863 and Ticket 1029188).

### Missing Evidence
*   **Specific Product Details:** The exact eBook/Presentation Plus title and ISBN being downloaded.
*   **Unit/Component Count:** The total number of units/PEs included in the failing eBook.
*   **Application Logs:** Desktop client logs to confirm whether background extraction is ongoing or if an unzipping error/network timeout is occurring.

## Actions Performed in Similar Incidents
*   **Ticket 1077440:** Tested and confirmed that books download successfully on the backend despite UI showing 98%. Advised users to resume by clicking "play" rather than canceling or uninstalling. Opened discussion with CUP regarding UI feedback loop and timer behavior.
*   **Ticket 1029188:** Verified behavior in production. Determined it was "working as per design" because ~150 small linked PE units were unzipping in the background before the main eBook download started. Advised user to let the background process finish.
*   **Ticket 938863:** Replicated in the THOR environment using test accounts. Engineering implemented a code fix to improve the progress percentage calculation logic for products with >100 units. Tested and verified the fix in QA and REL environments before release.
*   **Ticket 1043393:** Replicated using THOR code and Production DB build. Identified that incomplete/corrupted zip files blocked the unzip sequence. Resolved the issue via patch **COS-1186** to support graceful recovery.
*   **Ticket 1055614:** Investigated large-file (4 GB) presentation downloads. Verified that post-incident production improvements **COS-1186** and **NEMO-14974** successfully stabilized the pause/resume functionality during network interruptions.

## Recommended Investigation Steps
1.  **Identify the Target Product:** Request the specific ISBN and title of the eBook the user is trying to download to verify if it has a high unit count (>100 units) or large Presentation Plus components.
2.  **Verify Backend Progress:** Check if the book successfully extracts and downloads locally on the user's disk despite the UI indicating a stuck status (cross-reference with **Ticket 1077440** and **Ticket 1029188**).
3.  **Inspect App Logs for Zip Corruptions:** Check for unzip/extraction exceptions or network timeout errors within the desktop application logs to determine if the download is physically blocked (cross-reference with **Ticket 1043393**).
4.  **Replicate in Environment:** Attempt to replicate the download of the same eBook title within the THOR environment to monitor progress calculation behavior (cross-reference with **Ticket 938863**).

## Recommended Resolution Path
1.  **Workaround/User Advice:** If the product has a high unit count, advise the user to wait without pausing, as the background extraction of PE units may take several minutes while the progress bar remains stationary (working as per design). If it halts entirely, advise them to use the play/resume function.
2.  **Engineering Escalation:** If logs reveal that the unzip process is failing or the progress timer is looping infinitely:
    *   Coordinate with the development team to review UI timer behavior for small multiple zip files.
    *   Verify if the latest patches (**COS-1186** and **NEMO-14974**) are fully active and up to date on the user's installed desktop client version.

*   Background processing of many small linked units (Ticket 1029188, Ticket 938863).
*   Incomplete file-handling errors (Ticket 1043393).

The pattern of the UI progress indicator losing synchronization with backend background processes perfectly aligns with the reported behavior.
