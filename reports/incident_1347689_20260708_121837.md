# Operational Incident Investigation Report

1347689

## Reported Issue Summary
A teacher is experiencing an issue where access lock rules created for the "Ready, Set, Grow! (American English) Level 1" Home Practice section are not taking effect. Although the platform successfully displays a confirmation message indicating the rules have been saved and lists the active rules in the interface, the exercises remain completely accessible to students as if no lock rules had been applied.

## Common Patterns Identified
*   **Platform-Wide Lock Rule Behavior:** Across Cambridge One, lock rules configured via the "Manage Student Access" menu are prone to either corruption or processing blocks that fail to enforce the UI restrictions.
*   **Rule Corruption / Silent Failures:** As seen in Ticket 1299299 and Ticket 1312794, Lock Rules can silently corrupt. When corrupted, the UI indicates that rules exist, but the actual entitlement/lock enforcement fails, allowing unrestricted access or causing redirect loops.
*   **Re-saving to Clear State:** A recurring resolution pattern for silent rule failures on Cambridge One involves opening the existing rule configurations and re-saving them to force the system to rebuild the rule association.

## Root Cause Analysis

*   **Confirmed causes:** 
    *   The automated replication script failed because it encountered a login wall (`Page title: Log in | Cambridge One`), indicating that credentials/session tokens were required to access the specific class URL. No backend rule failure could be validated via automation.
*   **Suspected causes:**
    *   **Lock Rule Corruption:** Similar to Ticket 1299299 and Ticket 1312794, the newly created Lock Rule for the "Ready, Set, Grow! Level 1 - Home Practice" section may be corrupted in the database, preventing the platform from translating the rule into actual access restrictions for students.
    *   **Incomplete Item Mapping:** Similar to Ticket 1038544, there may be an offset or delay between the items selected in the "Create access rule" screen and the items actually committed to the lock configuration database table.
    *   **Non-Lockable Component:** The "Home Practice" component for this specific product might be registered as an un-lockable element (similar to issues tracked under Jira ticket **NEMO-21735**), meaning the interface allows rule creation but the backend engine ignores locks on this resource type.
*   **Missing evidence:**
    *   API and database logs for class `e714cef1-e9f4-41f2-903c-052710c9e430` confirming if the rule payload was properly written.
    *   Validation of student enrollment state to confirm if any historical user scope rules exist for removed students (as in Ticket 1099646 / COS-1424).

## Actions Performed in Similar Incidents
*   **Ticket 1099646:** Support validated replication steps, identified user scope conflicts, and engineering resolved the processing block via code fix **COS-1424**.
*   **Ticket 1299299:** Support replicated the issue using the affected student account, located the specific corrupted "Lock Rule 8", opened the rule in the backend/UI, and re-saved it without changes, restoring normal lock behavior.
*   **Ticket 1312794:** Support located the corrupted lock rule (Rule Id: hPTT8uVwL0hsyoG5), re-saved the rule to clear the error state, and linked the issue to **COS-2229** for further investigation by the **RED team**.
*   **Ticket 1038544:** Engineering analyzed API and application logs, cross-referencing activity item codes and transaction timestamps, discovering that rules were applied after the students' activity occurred.

2.  **Verify Class List Consistency:** Check if any students have been recently removed or un-enrolled from class `92h2-mQi7` that might have had individual lock rules applied to them, triggering a rule-saving conflict (derived from *Ticket 1099646 / COS-1424*).
3.  **Check Component Lock Compatibility:** Verify via database or platform configuration whether the "Home Practice" component for *Ready Set Grow!* is classified as a lockable asset, or if it is being excluded (referencing Jira **NEMO-21735**).

## Recommended Resolution Path
1.  **Primary Action:** Have the Support team or the teacher edit and re-save the created lock rule within the class dashboard. This often resolves active session corruption on Cambridge One.
2.  **Escalation Path:** If re-saving does not enforce the lock, escalate the incident to the **RED team** referencing ticket **COS-2229** and Jira **NEMO-21735** to verify if a platform-level patch is required for the *Ready Set Grow!* Home Practice asset scope.
