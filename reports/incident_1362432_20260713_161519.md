# Operational Incident Investigation Report

## Incident Number
1362432

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
The user experienced an "unknown error" warning when initially trying to activate an access code on Cambridge One. Upon attempting to submit the same activation code a second time, the platform indicated that the code had already been used. Navigating back to the dashboard confirmed that the product was successfully activated, indicating that while the activation database write succeeded, the user interface and frontend system state failed to sync or update correctly during the initial process.

## Initial Assessment
- **Likely Affected Systems:** Cambridge One (C1) Platform, PEAS (Product Entitlement and Activation System)
- **Likely Affected Products:** Cambridge One Digital Products / Courseware (ELT Platform)
- **Likely Affected Components:** Activation UI Module, Entitlement Sync Service, micro-nemo (Microservice for user entitlements/activation UI states)

## Common Patterns Identified
1. **The PEAS-C1 Handshake Desync:** When a user submits an activation code, Cambridge One communicates with the PEAS backend. If PEAS returns an unexpected response or latency occurs, Cambridge One throws a frontend error. However, PEAS registers the code as activated.
2. **Ghost Activation UI State:** The backend entitlement database update successfully processes, but the UI state is not dynamically refreshed or displays a false-negative error message.
3. **Manual Refresh Mitigation:** Navigating away (e.g., back to the dashboard) or initiating a manual "refresh entitlement" triggers a fresh query to PEAS, which resolves the visual display and makes the product accessible.

## Root Cause Analysis

### Confirmed Causes
- **UI Refresh Failures:** The current replication attempt confirms the visual state is inconsistent. The code is recorded as "used" on the second attempt because the first attempt successfully wrote to the backend database despite throwing an initial visual error.

### Suspected Causes
- **PEAS Response Error Handling:** C1 is receiving an unexpected payload format or response code from PEAS during the active HTTP request sequence, causing the UI to break and display an "unknown error" even though the database transaction committed.
- **Component-Specific UI State Failures:** The active component (similar to the Presentation Plus component in Ticket 1022078) may be failing to call the state reload function on micro-nemo post-activation.

### Missing Evidence
- **Backend Application Logs:** Kibana/system application logs corresponding to the timestamp of the "unknown error" generated on the user's account.
- **Network Payloads (HAR files):** The precise API response payload returned by PEAS during the initial activation call to verify if it was a 500-series error, a timeout, or an unhandled JSON structure.

## Actions Performed in Similar Incidents
- **Ticket 1007467:** Investigated log files and identified unexpected responses from PEAS. Executed a manual "refresh entitlement" for the user. Linked the issue to development ticket **COS-1004** for log improvement releases.
- **Ticket 1007937:** Performed a manual "refresh entitlement" via the support console to restore product access in C1. Tracked underlying resolution through **COS-1004** (April 27th release).
- **Ticket 1007941:** Performed a manual "refresh entitlement" for the impacted user. Linked error tracking to **COS-1004** and assigned to the Compro team for verification.
- **Ticket 1022078:** Replicated the product bundle issue in the THOR environment. Identified missing automatic state refresh calls on the micro-nemo microservice. Resolved by deploying a microservice update (tracked under **COS-1096** / Jira) to force dynamic UI updates.
- **Ticket 1006931:** Manually refreshed user entitlements. Analyzed logs pointing to PEAS unexpected responses and categorized them under **COS-1004**.

## Recommended Investigation Steps
1. **User Entitlement Check:** Query the user identifier (UID) for testing account `prodlitmust2@mailsac.com` to verify if all expected components are synced in the backend database. (Source: Ticket 1007467)
2. **Examine Microservice Logs:** Search Kibana/APM logs for the activation timestamp, targeting errors related to `micro-nemo` or PEAS API calls to identify if an unexpected payload is being returned. (Source: Ticket 1022078, Ticket 1007937)
3. **Reproduce in Staging (THOR):** Replicate the activation flow using a similar bundle structure in the THOR test environment to observe the HTTP request-response cycle. (Source: Ticket 1022078)

## Recommended Resolution Path
1. **Short-Term Workaround:** If production end-users are impacted by missing entitlements after seeing this error, support must execute a manual **"refresh entitlement"** sequence to force UI synchronization.
2. **Long-Term Engineering Fix:** Refer this case to the **Compro** development team to inspect the error handling logic during activation. Ensure that if PEAS successfully registers the activation, C1 ignores non-critical API response errors and forces a dashboard-wide entitlement state update, preventing the "unknown error" banner from displaying (similar to the **COS-1096** fix implemented for Presentation Plus).

## Confidence Level
**High**

### Explanation
There is a clear, recurrent pattern of Cambridge One throwing error messages during activation due to unexpected PEAS API interactions, despite the backend transactions completing successfully. Five historical incidents (specifically Ticket 1022078 and Ticket 1007467) demonstrate this exact behavior where users must navigate away or manually refresh the page/entitlements to see their activated products on the dashboard.
