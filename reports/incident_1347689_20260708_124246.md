# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
The teacher is reporting that the Lock/Unlock rules are not functioning as expected within the "Home Practice" section of *Ready, Set, Grow! (American English) Level 1*. Although the teacher is able to create and save the lock rule interface with a success confirmation, the designated exercises remain fully accessible to students as if no rule had been created.

## Common Patterns Identified
Across the analyzed historical tickets, a few critical technical patterns emerge:
1. **Rule State Corruption on Cambridge One:** Lock Rules often experience backend/database corruption. While the UI might falsely report a successful operation (or a continuous loading loop), the actual access validation engine fails to enforce the lock.
2. **"Re-Saving" Bypass:** In multiple scenarios (Ticket 1299299 and Ticket 1312794), simply opening the corrupted rule and saving it again without making any modifications forced the platform to re-evaluate, clear the corruption, and properly apply the lock state.
3. **Class Roster Synchronization Discrepancies:** Lock rules frequently fail to update or enforce properly if a user scope lock is associated with a student who was recently deleted or removed from the class (as tracked under COS-1424).

## Root Cause Analysis
Based on the current incident and historical evidence:

- **Confirmed causes:** None at this initial stage.
- **Suspected causes:** 
  - **Lock Rule Corruption:** Similar to Ticket 1299299 and Ticket 1312794, the Lock Rule generated for class `92h2-mQi7` may have corrupted during writing, preventing the frontend engine from recognizing that the Home Practice content should be blocked.
  - **Removed/De-provisioned Learner Conflict:** A student previously associated with a user-scope lock might have been removed from class `92h2-mQi7`, causing validation execution errors during rule evaluation (related to COS-1424).
  - **Item Code Configuration Delay:** The specific items under "Home Practice" might not have been correctly registered or updated in the active rule configuration timeframe (similar to Ticket 1038544).
- **Missing evidence:**
  - Database records showing the exact rule parameters and Rule ID generated for class `92h2-mQi7`.
  - Application logs (such as `sdk.config.get` responses or Gigya authentication validation logs).
  - Roster history to check if any students were deleted or moved from the class.

## Actions Performed in Similar Incidents
- **Ticket 1299299:** Support replicated the issue via the affected user's account, identified a corrupted rule ("Lock Rule 8"), and resolved it by opening and re-saving the rule to clear the corruption.
- **Ticket 1312794:** Technical analysis checked Gigya login tokens and API configurations (`sdk.config.get`). The support team located the corrupted Rule Id (`hPTT8uVwL0hsyoG5`), re-saved it without changing any parameters, and confirmed access was restored. Escalated to the **RED team** under **COS-2229**.
- **Ticket 1099646:** Validated replication steps where user-scoped locks for removed learners caused infinite saving loops. This was resolved by the engineering team deploying a fix to **THOR** under **COS-1424**.
- **Ticket 1038544:** Engineering analyzed API and application logs (specifically tracking `ItemCodes` modifications) to verify if rules matched student submission timestamps (NEMO).

## Recommended Investigation Steps
1. **Re-Save the Rule (Quick Win):** Access the teacher account or class management console for class `92h2-mQi7`, open the newly created Home Practice Lock Rule, and click "Save" again without making any modifications. Test if this forces the system to sync and apply the lock (Derived from Ticket 1299299, Ticket 1312794).
2. **Review Class Roster for Deleted Students:** Cross-reference active class participants with database records of the created lock rule to ensure no user-scope rules are bound to a learner who has left the class (Derived from Ticket 1099646 / COS-1424).
3. **Verify API/Database Rule Registration:** Query the backend using the class ID (`e714cef1-e9f4-41f2-903c-052710c9e430`) to extract the exact generated `Rule ID` and confirm that all selected Home Practice `ItemCodes` are properly tied to the lock rule configuration (Derived from Ticket 1038544).

2. If the re-save fails, escalate to the **RED team** referencing **COS-2229** or check for a platform-wide regression similar to **COS-1424** / **NEMO-21735**.
