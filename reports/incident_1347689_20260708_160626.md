# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
The teacher is reporting that the lock rules feature is not functioning as intended for the course "Ready, Set, Grow! (American English) Level 1" in the "Home Practice" section. Although the teacher is able to navigate the "Manage Student Access" interface, create a lock rule for selected exercises, and receive a success confirmation message, the selected exercises remain fully accessible to the students as if no restrictions had been applied.

## Initial Assessment
*   **Affected Platform:** Cambridge One (C1)
*   **Affected Product:** Ready Set Grow! (American English) Level 1
*   **Affected Class Code/Key:** 92h2-mQi7
*   **Affected Components / Interface:** Manage Student Access -> Home Practice / Lock Rules configuration interface
*   **Likely Impacted Systems:** Rules Engine / Lock Rule configuration backend (NEMO / ELT Platform)

## Root Cause Analysis

### Confirmed causes
*   *None confirmed at this stage for the current incident pending direct backend/API log inspection.*

### Suspected causes
*   **Lock Rule Corruption:** Similar to **Ticket 1299299** and **Ticket 1312794**, the newly created Lock Rule may be corrupted or failing validation during execution, preventing the system from applying the restrictions to the student views.
*   **Student Membership Mismatch / Invalid Scope:** Similar to **Ticket 1099646** (COS-1424), if there are inconsistencies with student enrollment, or if a student was removed/added during the rule creation, the rule processing engine may silently fail to bind the lock to active learners.
*   **Incomplete Backend Item Association:** Similar to **Ticket 1038544**, the application UI might save the rule successfully, but the specific item codes for "Ready Set Grow! Level 1 Home Practice" may not have been correctly packaged or written to the rule database.

### Missing evidence
*   Backend API logs showing the JSON payload when "Save" is clicked for this rule.
*   The generated `Rule ID` for the newly created lock rule.
*   Student roster confirmation to check if any students were recently removed or modified in Class Code `92h2-mQi7`.
*   Direct verification of whether this course/component contains non-lockable materials (referencing **NEMO-21735**).

## Actions Performed in Similar Incidents
*   **Ticket 1099646:** Replicated by creating a user-scope lock rule and removing a learner. Verified the saving issue via **COS-1424** and deployed a fix to **THOR**.
*   **Ticket 1299299 & Ticket 1312794:** Located the affected Lock Rule ID, opened the rule in the administration/teacher interface, and re-saved the rule without modifications. This cleared the corruption state on the database side and restored proper access enforcement.
*   **Ticket 1038544:** Analyzed API and application logs to verify rule creation timestamps and cross-referenced them with specific ItemCodes to confirm if the items were explicitly included in the lock configuration.

## Recommended Investigation Steps
1.  **Re-save the Rule (Immediate Workaround Attempt):** Instruct the teacher to open the created lock rule for the "Home Practice" section and re-save it without making changes to see if it clears any initial database write corruption (**Ticket 1299299**, **Ticket 1312794**).
2.  **Verify Item Configuration via API Logs:** Check backend API logs to ensure the item codes for "Ready Set Grow! Level 1 Home Practice" are successfully mapped to the Lock Rule payload (**Ticket 1038544**).
3.  **Check Class Roster and Membership Consistency:** Inspect if any student accounts in class `92h2-mQi7` are in an orphaned, pending, or recently deleted state which could disrupt rule mapping (**Ticket 1099646** / **COS-1424**).
4.  **Confirm Component Lockability:** Ensure that the "Home Practice" components do not fall under non-lockable category types managed by the RED/NEMO development teams (**NEMO-21735**).

## Recommended Resolution Path
*   If the issue is caused by a corrupted write state, **re-saving the rule** via the UI or resetting it on the database backend will resolve it.
*   If a specific student account or membership mismatch is blocking the rules engine, coordinate with the development team to handle exception processing or clean up orphaned users within class `92h2-mQi7`.
*   If structural component mapping is failing, escalate to the **RED team** referencing ticket tracking pattern **COS-2229** or **NEMO-21735**.
