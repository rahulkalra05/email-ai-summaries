# Operational Incident Investigation Report

## Reported Issue Summary
A teacher is unable to restrict student access using the "LOCK" rules feature within Cambridge One for "Ready, Set, Grow! (American English) Level 1 - Home Practice" (Class Key: 92h2-mQi7). Although the interface displays a success confirmation message after the teacher selects the exercises and saves the rule, the lock rules are not enforced. Students are still able to access the materials freely as if no restriction rule had been created.

## Common Patterns Identified
Across the reviewed historical tickets, several core patterns emerge regarding Lock Rules on Cambridge One:
- **Lock Rule Corruption:** A very common pattern is where a Lock Rule becomes corrupted or enters an invalid state (Ticket 1299299, Ticket 1312794). This corruption often manifests as an absolute block (redirecting students to the dashboard) or a total failure of rule validation (allowing access). 
- **The "Re-Save" Fix:** When rules are corrupted or fail to enforce/clear, opening the affected Lock Rule and saving it again without making any modifications updates the rule's active state in the database and resolves the issue.
- **Roster Changes / Invalid States:** Changes to the class roster (such as removing a student who had an individual user-scope rule assigned) can cause the lock rule system to fail silently or prevent rule changes from compiling correctly (COS-1424 / Ticket 1099646).

## Root Cause Analysis

- **Confirmed causes:** 
  - None at this stage, as direct application/API logs for Class Key `92h2-mQi7` have not yet been extracted.
- **Suspected causes:**
  - **Lock Rule Corruption (Pattern-Based Inference):** The configuration rule generated by the teacher's save action is corrupted, preventing the system from validating and enforcing the lock constraints when a student attempts to open Home Practice.
  - **User Roster Inconsistency (Pattern-Based Inference):** There may be a student who was previously assigned a custom rule or who has been removed/modified in the class roster, preventing the system from successfully compiling and applying updates to the class-wide Lock Rules.
  - **As-Per-Design Timing Issue:** The teacher may have verified student access prior to the exact timestamp the rule was registered/updated on the server side, or the specific sub-items under "Home Practice" were not fully included in the saved rule configuration (similar to Ticket 1038544).
- **Missing evidence:**
  - API logs showing the JSON payload when the teacher clicks "Save" and receives the confirmation message.
  - Database status of the generated Rule ID for Class Key `92h2-mQi7` to determine if it is registered as active.
  - Verification of whether any students in the class have custom user-scoped lock rules applied, or if any students were recently removed from the class roster.

## Recommended Resolution Path
1. **Administrative Re-Save:** Open the affected "Home Practice" Lock Rule within the class configuration interface and save it again without modifying any parameters. This is the most common resolution for rule sync failures and corruption on Cambridge One.
2. **Escalation to RED Team / COS-2229:** If re-saving does not resolve the issue, escalate the incident to the **RED team** referencing **COS-2229** and **COS-1424** to inspect the lock database schema for orphaned student entries or database validation errors preventing the rule from executing.

## Confidence Level

**Explanation:**
The reported issue has a strong match to the Cambridge One platform and the Lock Rules module. However, the exact failure state is inverted: instead of blocking student access (as in Ticket 1299299 and Ticket 1312794), this issue fails to restrict student access. This indicates either a silent corruption of the rule validation engine (which bypasses checks entirely) or a roster synchronization issue (COS-1424), requiring log analysis to definitively isolate the root cause.
