# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
A teacher using *Ready, Set, Grow! (American English) Level 1* is unable to effectively lock exercises via the "Manage Student Access" feature on Cambridge One. Although the interface proceeds through the rule creation workflow, the system returns an error message upon saving, and the exercises remain accessible to students.

## Initial Assessment
The issue is localized to the "Manage Student Access" module within the Cambridge One platform. Affected components include the rule creation engine and the database persistence layer responsible for entitlement/lock status.

## Common Patterns Identified
Across multiple incidents (1299299, 1312794), a recurring pattern is the **corruption of existing Lock Rules**, which leads to unexpected UI behavior or a total failure to enforce restrictions. Additionally, Ticket 1099646 confirms that external factors (e.g., removed students) can cause the "Save" function to fail (COS-1424).

## Root Cause Analysis
- **Confirmed causes:** None yet confirmed for this specific ticket.
- **Suspected causes:**
    1. Corruption of the existing Lock Rule configuration for the specified class.
    2. A transient validation failure triggered by the "Save" process (similar to 1102122).
    3. Potential "user scope" interference caused by student enrollment changes (as evidenced in COS-1424).
- **Missing evidence:** Access to application logs (e.g., `sdk.config.get` status) and database integrity checks for the specific `Rule Id` associated with the affected class.

## Actions Performed in Similar Incidents
- **Ticket 1099646:** Replicated steps and confirmed via Engineering (COS-1424) that removal of students causes save failures.
- **Ticket 1299299:** Replicated using affected user account; resolved by opening and re-saving the rule to clear corruption.
- **Ticket 1312794:** Identified corrupted `Rule Id` (hPTT8uVwL0hsyoG5), re-saved the rule to restore functionality, and escalated to the RED team (COS-2229).
- **Ticket 1038544:** Analyzed API logs and verified timestamp alignment; determined the issue was "As Per Design."

## Recommended Investigation Steps
1. **Rule Integrity Check:** Attempt to open and re-save the existing lock rule for the affected class (Class Code: 92h2-mQi7) to determine if it clears the error, as seen in Ticket 1299299.
2. **Review Class Enrollment:** Check if any learners were recently removed from this class, which may be triggering a validation error during the save process (Procedure: COS-1424).
3. **Log Analysis:** Utilize platform logs to check for `sdk.config.get` errors or entitlement validation failures during the "Save" event (similar to Ticket 1312794).
4. **Item Verification:** Cross-reference the specific exercise items selected with the lock rule criteria to ensure the selection is valid (Reference: Ticket 1038544).

## Recommended Resolution Path
If re-saving the rule fails, escalate to the Engineering/RED team to inspect the `Rule Id` for corruption. If the rule is found to be corrupted, trigger a reset of the rule parameters via the back-end as per the resolution pattern in COS-2229. If the error persists, check for orphan user references in the rule scope (COS-1424).
