# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
A teacher has reported that the "Lock" rules under "Manage Student Access" are not working for the course "Ready, Set, Grow! (American English) Level 1" in the Home Practice section. Although the platform displays a confirmation message indicating that the access rule was created successfully, the selected exercises are not actually locked and students can still access them freely.

## Initial Assessment
*   **Affected Platform:** Cambridge One
*   **Affected Product:** Ready Set Grow! (American English) Level 1
*   **Affected Component:** Manage Student Access (Lock Rules / Home Practice)
*   **Affected Class Details:** Class Code/Key: `92h2-mQi7`, Course URL: `https://www.cambridgeone.org/class/teacher/teacher_clms_4629756/class/e714cef1-e9f4-41f2-903c-052710c9e430/view/materials`

## Common Patterns Identified
*   **Lock Rule State Corruption:** Across Ticket 1299299 and Ticket 1312794, existing Lock Rules became corrupted in the system. The symptoms included rules failing to enforce expected UI behaviors (such as hiding/locking content or displaying "The content is currently locked" messaging) or blocking user entitlements entirely.
*   **Rule Enforcement Failures / Desync:** Lock rules sometimes fail to apply because of mismatching item configurations or timestamps (as seen in Ticket 1038544), where the platform technically saves a rule successfully, but the actual target resources (ItemCodes) are not properly bound to the active rule restriction.
*   **Enrollment State Conflicts:** Changes in class rosters (such as removing a student who has an active user-scoped lock rule, as seen in Ticket 1099646) cause backend exceptions that disrupt rule processing and state synchronization.

## Root Cause Analysis
*   **Confirmed causes:** None at this stage, as direct backend database and application log analysis has not yet been executed for this specific class.
*   **Suspected causes:**
    1.  **Rule Metadata Corruption:** The Lock Rule created by the teacher may have saved in a corrupted state, preventing the underlying components from evaluating the lock restrictions against student sessions (similar to Tickets 1299299 and 1312794).
    2.  **Item Binding Failure (As-Designed Sync Delay):** The specific exercises selected for "Home Practice" may not have mapped correctly to the rule configuration database, meaning the rules exist but point to null or incorrect resource identifiers (similar to Ticket 1038544).
    3.  **Roster Sync Anomalies:** The class `92h2-mQi7` may contain inactive, unlinked, or corrupted student accounts (Gigya/SAP-CDC tokens) that are breaking the evaluation loop for class-wide lock rules (similar to Ticket 1099646).
*   **Missing evidence:**
    *   API response payloads for rule creation under the affected class ID `e714cef1-e9f4-41f2-903c-052710c9e430`.
    *   Verification of student roster states and active Gigya login tokens.
    *   Specific ItemCodes associated with the Home Practice section of "Ready Set Grow! Level 1".

## Actions Performed in Similar Incidents
*   **Ticket 1099646:** Replicated lock rule-saving issues, identified a user scope rule conflict for a removed learner, verified behavior under COS-1424, and deployed a fix to the THOR environment.
*   **Ticket 1299299:** Replicated access issues for the student, identified the corrupted "Lock Rule 8", and forced a state refresh by opening and re-saving the rule without making modifications, which resolved the corruption.
*   **Ticket 1312794:** Inspected application logs (specifically searching for `sdk.config.get` and Gigya token errors), identified the corrupted rule (`Rule Id: hPTT8uVwL0hsyoG5`), re-saved the rule to clear the error state, and linked the issue to COS-2229 for investigation by the **RED team**.
*   **Ticket 1038544:** Analyzed API logs to cross-reference student submission timestamps with rule modification timestamps and checked specific ItemCodes. Verified that the rules did not contain the items at the time of student activity.
*   **Ticket 1102122:** Reviewed the class configuration and application logs, but was unable to replicate the issue because the transient save state resolved on its own.

## Recommended Investigation Steps
1.  **Re-save the Lock Rule:** Have the teacher or an internal support agent open the newly created lock rule for "Home Practice" on the class materials page and click "Save" again without changing any parameters. This is the quickest way to force a metadata refresh and clear rule corruption (Reference: **Ticket 1299299**, **Ticket 1312794**).
2.  **Inspect Active Lock Rule Configuration via API:** Retrieve the JSON payload of the active lock rules for class `e714cef1-e9f4-41f2-903c-052710c9e430`. Cross-reference the selected "Home Practice" exercises with the item IDs registered within the lock rule to ensure they are bound correctly (Reference: **Ticket 1038544**).
3.  **Verify Roster Integrity:** Check the class roster for any pending, inactive, or recently removed student accounts. Ensure that no orphan user-scope rules exist in the class database that could be halting the rule-processing engine (Reference: **Ticket 1099646**, **COS-1424**).

## Recommended Resolution Path
If re-saving the rule does not force-refresh the lock state, the incident should be escalated to the **RED team** under the parent tracking ticket **COS-2229** / **NEMO** platform queue to verify if a database-level corruption exists on the rule mapping for this specific product cohort.
