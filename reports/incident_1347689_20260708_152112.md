# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
A teacher is experiencing an issue where lock rules created via "Manage student's access" are not functioning for the course "Ready Set Grow! (American English) Level 1" (Home Practice section). Although the platform displays a confirmation message that the rule has been successfully saved, the exercises remain fully accessible to students as if no lock rules had been applied.

## Initial Assessment
* **Affected Product:** Ready Set Grow! (American English) Level 1
* **Affected Class Code/Key:** 92h2-mQi7
* **Affected Course URL:** `https://www.cambridgeone.org/class/teacher/teacher_clms_4629756/class/e714cef1-e9f4-41f2-903c-052710c9e430/view/materials`
* **Affected Components:** Cambridge One (C1) Platform, "Manage Student Access" workflow, Home Practice section, Lock/Unlock rule validation system.

## Common Patterns Identified
* **Lock Rule State Corruption:** Multiple historic tickets (Ticket 1299299, Ticket 1312794) show that the Cambridge One platform can experience localized database or state corruption for specific Lock Rules. This results in validation failures where rules exist on the interface but are not enforced by the backend entitlement engine.
* **Class Roster / User Scope Discrepancies:** Ticket 1099646 highlights that modifying class rosters (e.g., removing a student) while a personalized or user-scoped lock rule is active can break rule processing logic on the backend.
* **Component-Level Locking Constraints:** Backend configurations and changes (such as those associated with NEMO-21735) can prevent certain non-lockable components from behaving correctly under standard lock rules.

## Root Cause Analysis

### Confirmed Causes
None at this stage due to the automated replication script failing during the login phase (unable to verify the "Hi Litmus!" dashboard state).

### Suspected Causes
1. **Rule State Corruption:** Similar to Tickets 1299299 and 1312794, the Lock Rule generated for class `92h2-mQi7` may have corrupted during the save operation, displaying a success toast in the UI while failing to update the access control database.
2. **Missing Rule Scope Items:** As seen in Ticket 1038544, the rule might have been successfully saved but did not explicitly bind or map to the active Home Practice content exercises in the backend.
3. **Orphaned User Scope Rule:** A student may have been added/removed or changed status in Class Key `92h2-mQi7`, triggering a processing failure in the rule engine similar to COS-1424.

### Missing Evidence
* API and database logs for Class Key `92h2-mQi7` to verify if the rule ID was actually generated and associated with the correct content item codes.
* Active roster history for Class `e714cef1-e9f4-41f2-903c-052710c9e430` to check for removed or modified students.

## Actions Performed in Similar Incidents
* **Ticket 1099646:** Replicated the rule-saving issue by establishing a user-scope lock rule and removing a learner. Engineering investigated the database state, tracked the issue via **COS-1424**, and deployed a backend fix to **THOR**.
* **Ticket 1299299:** Replicated using the affected student's account, identified the specific corrupt rule, and resolved the behavior by opening the rule configuration in the teacher panel and re-saving it.
* **Ticket 1312794:** Evaluated backend logs for **sdk.config.get** (returning 200 OK) and checked Gigya login tokens. Located the exact corrupted rule (**Rule Id: hPTT8uVwL0hsyoG5**) and re-saved it without changes. Escalated the underlying root cause to the **RED team** via **COS-2229**.
* **Ticket 1038544:** Engineering analyzed API logs, verified rule creation timestamps, and cross-referenced them with student submission timestamps to check if items were configured in the rules during active windows.
