# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
A teacher is unable to restrict student access using the "LOCK" rules function under "Manage student's access" for the course "Ready Set Grow! (American English) Level 1" in the "Home Practice" section. Although the platform displays a successful confirmation message indicating that the access rule was created and saved, the exercises remain completely accessible to students as if no lock rules were applied.

## Common Patterns Identified
*   **Platform & Feature Specificity:** All historical incidents occur on the Cambridge One platform and specifically involve the "Manage Student Access" / "Lock Rule" configuration module.
*   **Functional Failures vs. Silent Failures:** When lock rules do not apply or cause platform errors, the root cause is frequently linked to either a mismatch in class enrollment (e.g., student removed while associated with a rule) or corruption within the specific Lock Rule database record/ID.
*   **Resolution via Rule Re-Saving:** In multiple instances where lock rules failed to execute correctly (Ticket 1299299, Ticket 1312794), the error state was cleared simply by opening, minorly adjusting (or leaving as-is), and re-saving the rule to force the backend to rewrite the rule parameters.

## Root Cause Analysis

*   **Confirmed causes:** None at this stage, as the local replication attempt failed due to a syntax error in the automation script.
*   **Suspected causes:**
    1.  **Rule Corruption / Validation Failure:** Similar to Ticket 1299299 and Ticket 1312794, the created Lock Rule record might be corrupted on creation or during evaluation, causing the platform to fail to apply the lock constraints silently.
    2.  **Enrollment Sync Discrepancies:** Similar to Ticket 1099646 (COS-1424), if a student was recently added, removed, or has an inactive enrollment status in class `92h2-mQi7` while a rule is being applied, the system may fail to process the scope properly.
    3.  **Specific Content Unlockable:** The Home Practice section of "Ready Set Grow!" might contain elements that are non-lockable, causing the rule to silently ignore them (similar to NEMO-21735 behavior).
*   **Missing evidence:**
    1.  Application/API logs from the backend during the time the teacher (Madz Suarez / Class Key: 92h2-mQi7) saves the rule.
    2.  Active lock rule payload verification via database or API check to see if the item IDs for "Home Practice" are correctly appended.
    3.  Verification of student roster history to check if any students were deleted or moved.

## Actions Performed in Similar Incidents
*   **Ticket 1099646:** Replicated the rule-saving issue by establishing a user-scoped lock rule, removing the associated learner from the class, and attempting to update the rule. This behavior was confirmed as a system bug and tracked under engineering ticket **COS-1424** (deployed to THOR).
*   **Ticket 1102122:** Searched application logs for errors related to lock rules and reviewed the active class state.
*   **Ticket 1038544:** Verified rule creation timestamps and modification logs via API logs. Cross-referenced student submission timestamps with rule update timestamps to determine if behavior was "As Per Design" (NEMO-14789).
*   **Ticket 1299299 & Ticket 1312794:** Identified the specific rule causing the error (e.g., Rule Id: hPTT8uVwL0hsyoG5), opened the rule configuration interface, and re-saved the rule without modification to clear database corruption. Ticket 1312794 linked this behavior to **COS-2229** for the RED team.

## Recommended Investigation Steps
1.  **Analyze API & Rule Logs:** Query API logs for class `92h2-mQi7` to check if the lock rule payload contains the correct ItemCodes for the "Home Practice" section, and confirm if they were added before the students accessed the material (derived from Ticket 1038544).
2.  **Inspect Active Roster:** Check the student roster for class `92h2-mQi7` to determine if any student accounts have been deactivated, deleted, or removed recently, which might trigger processing blockages similar to **COS-1424** (derived from Ticket 1099646).
3.  **Inspect Database Rule Records:** Query the rule database for the active Rule ID associated with this class to see if the record is registered as active or corrupted.
4.  **Fix and Re-run Replication Script:** Address the syntax error in `replication_scripts\replication_1347689_20260708_155754.py` (line 130 has nested unescaped double quotes inside the XPath string: `"xpath=//div[@id="__nuxt"]... "`) and re-run to confirm UI behavior.

## Recommended Resolution Path
1.  **Attempt Force Refresh (Re-save):** Access the teacher account or use administrative APIs to open the specific "Home Practice" lock rule created for class `92h2-mQi7` and click **Save** again. This simple overwrite frequently clears payload corruption (per Tickets 1299299 and 1312794).
2.  **Check for Non-Lockable Content (NEMO-21735):** If the content is structurally incompatible with locking, escalate to the **RED team** or product engineering to review if the component needs to be excluded or if a patch is required.
3.  **Clean Outdated User Rules:** If a student was removed, clear out orphaned user-scope rules for that class (per COS-1424).
