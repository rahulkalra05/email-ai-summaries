# Operational Incident Investigation Report

## Incident Number
1347689

## ⚠️ Verdict
**Requires Investigation**

## Reported Issue Summary
A teacher is experiencing an issue where the "LOCK" rules are not functioning as expected for the product "Ready, Set, Grow! (American English) Level 1" in the "Home Practice" section. Although the platform displays a confirmation message indicating that the access rule was successfully saved, the selected exercises remain unlocked and can be easily accessed by students without any restrictions.

## Initial Assessment
*   **Affected Platform/System:** Cambridge One (C1)
*   **Affected Product:** Ready Set Grow! (American English) Level 1
*   **Affected Components:** Manage Student Access (Lock/Unlock Rules interface), Home Practice section
*   **Affected Course/Class Link:** `https://www.cambridgeone.org/class/teacher/teacher_clms_4629756/class/e714cef1-e9f4-41f2-903c-052710c9e430/view/materials` (Class Key: 92h2-mQi7)

## Common Patterns Identified
*   **Lock Rule Corruption:** Across multiple historical incidents (Ticket 1299299, Ticket 1312794), Lock Rules became corrupted in the backend, preventing the UI from properly enforcing limits or causing validation loops. Re-saving the rule without modification often cleared the corrupted state.
*   **Student Membership Desync:** Out-of-sync roster states (e.g., Ticket 1099646) where a lock rule is targeted at a user who has been removed from the class causes the rule-saving and application pipeline to fail.
*   **Item Configuration Discrepancies:** As seen in Ticket 1038544, discrepancies between the exact items targeted by the lock rule and the active student interface items can lead to instances where rules appear "saved" but do not apply to the activities students are accessing.

## Root Cause Analysis

*   **Confirmed causes:** None at this stage. The replication attempt on the live environment failed due to a login script timeout on the Gigya form wrapper (`prodlitmust2@mailsac.com` authentication failed to proceed).
*   **Suspected causes:** 
    1.  **Rule Corruption / Validation Failure:** The lock rule generated is corrupted in the backend, meaning that while the UI registers a successful "Save" event, the backend fails to apply the validation rules (similar to Ticket 1299299 and Ticket 1312794 under Jira task `COS-2229`).
    2.  **Roster Inconsistency (User Scope Issue):** The class contains a modified roster or a student who was deleted/moved, causing rule processing to silently fail or not apply (similar to Ticket 1099646 under Jira task `COS-1424`).
    3.  **Non-Lockable Components:** The "Home Practice" component for this specific course might contain non-lockable assets or custom link structures that do not support lock rules (related to `NEMO-21735`).
*   **Missing evidence:**
    1.  Backend API request/response payloads for the lock rule creation API.
    2.  Application/API logs (e.g., Kibana) checking for any validation exceptions or database writing errors when saving rules for Class ID `e714cef1-e9f4-41f2-903c-052710c9e430`.
    3.  Verification of student roster history to confirm if any students were recently removed or modified in this class.

## Actions Performed in Similar Incidents
*   **Ticket 1099646:** Engineering validated the replication steps by creating user-scoped lock rules and removing a learner. Confirmed backend behavior, tracked via **COS-1424**, and deployed a fix to the THOR environment.
*   **Ticket 1299299:** Technical support replicated the issue with the student's account, identified the specific corrupted "Lock Rule 8", and resolved it by opening and re-saving the rule to clear the corruption.
*   **Ticket 1312794:** Support investigated application logs for Gigya tokens and entitlement validations (`sdk.config.get`). Located the corrupted rule (Rule Id: `hPTT8uVwL0hsyoG5`) and re-saved it without changing parameters to restore access. Linked the bug to **COS-2229** for the RED team.
*   **Ticket 1038544:** Verified rule creation timestamps and modification logs via API logs. Cross-referenced student submission timestamps with rule update timestamps, confirming behavior was as per design (NEMO-14789).

## Recommended Investigation Steps
1.  **Extract Rule and Course Details (Reference: Ticket 1299299, Ticket 1312794):** 
    Query the database or use API logs to locate the rule IDs created for Class `e714cef1-e9f4-41f2-903c-052710c9e430`. 
2.  **Verify Roster Alignment (Reference: Ticket 1099646):**
    Check if any students have been deleted, un-enrolled, or moved from the class since the start of the course, which might trigger the rule-saving bug (COS-1424).
3.  **Perform a Force Re-Save (Reference: Ticket 1299299, Ticket 1312794):**
    Have an administrator or the teacher open the newly created lock rule, make a minor edit (or keep it as is), and save it again to force a database write and clear potential initial payload corruption.
4.  **Audit Component Compatibility (Reference: NEMO-21735):**
    Verify if the "Home Practice" section contains assets that are classified as non-lockable, which would prevent the system from applying lock state constraints.

## Recommended Resolution Path
*   **If Rule Corruption is Identified:** Re-save the rule in the backend or have the teacher recreate it. If the issue persists, escalate to the **RED team** referencing **COS-2229** to investigate why rules for "Ready, Set, Grow! Level 1" are corrupting upon initial generation.
*   **If Roster Inconsistency is Identified:** Verify if the unresolved edge case from **COS-1424** (THOR/APP-side changes) is affecting this class and clean up the orphan user-scope configurations in the database.
